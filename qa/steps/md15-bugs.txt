### BUG-276 [MD-15] When both devices quarantine the same journal entry and one resolves it, the other keeps a stale conflict, keeps the old text at the cloud's version, and resolving it there (even with "Keep Remote") reverts the first device's resolution on every device
- Severity: Major
- Found: 2026-10-14, multi-device MD-15.4 (qa-081, debug build `58d4948` + Juno's parked-launch change), A = profile `qa`, B = profile `qb`
- Steps to reproduce: make an entry's cloud op log ambiguous so that **both** devices quarantine it as `corrupted_op_chain` (simulated: `qa/steps/md15-154-plant.dart.txt` with tag `dup_md15-je-06` on A appends two live character ops with the same position, clock and client, then rewrites the doc unchanged; A and B each record `journal_entries_md15-je-06`). On B: Resolve → edit the Manual merge field to "MD15 body 06 mergedb" → **Use merged text**. Then on A: Resolve → **Keep Remote**.
- Expected: B's resolution reaches A like any edit: A's row takes "MD15 body 06 mergedb", and A's conflict either clears or its dialog shows the current cloud copy. Choosing "Keep Remote" on A keeps the other device's (cloud) text.
- Actual: B's merge is correct in the cloud (v3, body "MD15 body 06 mergedb"; B's upload tombstoned the planted ops, so the chain resolves cleanly to that text). A takes v3 and B's `updated_at` but keeps the body "MD15 body 06" (`dbdiff.py`: `md15-je-06` body differs; A's full check `safe=true`, since it compares versions only). A's banner and dialog stay, and the dialog still shows the 14:35 snapshot (remote v1, body "XY"; `qa/shots/md15-154-qa-resolve.png`), so nothing tells A's user the conflict was settled elsewhere. A's **Keep Remote** then uploaded v4 with A's old body: B and the cloud dropped to "MD15 body 06", with B's " mergedb" characters tombstoned in the op log (`fs_ops.py … --chars`: 12 of 20 live). B's resolution is lost on every device, and the user chose "Keep Remote".
- Notes: a real corrupted chain (a third writer, or a reseed) is seen by every device that pulls it, so this is the normal case, not a harness artefact. The hardMetadataCollision case (crafted on A, `md15-154-collide.dart.txt`) was quarantined by B only and resolved cleanly with each of the three buttons. Related: BUG-247 (text loss after "Delete from Firestore"). Scatter on.

### BUG-277 [MD-15] Dev → "Purge soft-deleted items" purges only journal, to-do, calendar and tracker tombstones; dreams and every other kind past the 30-day window stay until the next launch
- Severity: Minor
- Found: 2026-10-14, multi-device MD-15.2 (qa-081, debug build `58d4948` + Juno's parked-launch change), A = profile `qa`
- Steps to reproduce: soft-delete an entry, a task, an event and a dream (`qa/steps/md15-152-tomb.dart.txt`), age their `deleted_at` 40 days back on A's database (`qa/steps/md15-152-age.py qa`, simulated retention), then Dev → **Purge soft-deleted items** on A.
- Expected: every tombstone past the retention window is removed, as the subtitle says ("Permanently remove items past the 30-day retention window"), the same set `SyncEngine.purgeExpiredDeleted` removes at launch.
- Actual: the entry, task and event rows are gone; the dream tombstone (`md15-dream-04`, `deleted_at` 2026-09-03) stays. The Dev tile calls `purgeExpiredDeleted` on four repositories (journal, to-do, calendar, trackers); the startup purge covers sixteen (also dreams, finance, LeetCode, study, workout, jobs, rankings, notifications, reminders, bucket list, settings).
- Notes: a Dev tool, so only developers see it; a relaunch purges the rest. The other device keeps its own tombstones either way (the purge is local, by design). Scatter on.
